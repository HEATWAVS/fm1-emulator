4. (Superseded: C3 and C4 are done.) C3/C4 approval: live conformance and failure tests, then firmware tests under each profile. The main technical risk to measure in C4 is host cost: a 2-20 ms WIP poll is about 0.2-2 M emulated cycles of real execution (the polling loop is not skipped), so firmware with many flash writes (coqui: about 1,200) will run slower under a profile.
5. The model refuses (throws) where the datasheets are silent or contradictory, e.g. UC25HQ80 chip erase at 14 of the 64 BP/CMP combinations (Puya's chip-erase rule is unambiguous and fully decided), WEL after rejected commands (list in FLASH-CHIPS.md). Should any be settled by probing a real unit?
6. Push to origin? Not done; only on request.
7. Is "both revisions use the AC791N" true for the newer unit? Unverified.
8. The CLI `--save-flash` / `--flash` round trip is still untested (listed in TESTING.md).

## Known risks
- **Unified engine (Component 8):** its hash is verified for one toolchain (rustc 1.97.1, Windows; the pipeline reproduced both engines there). It is a v0.3.0 base: newer upstream versions break the JIT host interface (`fm1_jit_compile` takes five arguments from v0.4.0) and change default timing and boot flash, so a rebase is a separate gated step (D94). Firmware built on the current felucca-bsp expects the audio PLL registers at the bootloader's values (upstream `d2bcc33`, v0.5.0); neither engine sets them, so such firmware can start silent. **USB audio-in: queue behaviour is verified (8 of 8 traces against the shipped engine); the sample content path (24- to 16-bit conversion, mono mix, 22.05 kHz resampling) is NOT verified.** The XIP-tail mode (`fm1_xip_tail`, default 0 = the shipped engine's) is not exposed in the application; which mode matches hardware is unknown. Chip test modes are FM-1 board only (SMK-37 firmware boots with an error telling you to use Default).
- The fork's compiled engine is not a build of the public upstream source (ARCHITECTURE.md). Chip behaviour beyond the ID exists only in the separately built chip-profile engine (v0.3.0-based: no USB host, the known **XIP-tail difference** (3,488 bytes at the end of the decoded XIP window, not investigated), **array-at-accept**: the array changes when a program/erase is accepted, not at the end of the cycle; a cycle running at power-off is treated as completing; **the `4Bh` unique ID value is unknown** (none unless a test configures one: answers FF, counted; firmware such as quadro-fm1 then falls back to its Bluetooth address); some datasheet behaviours are unspecified and are ignored and counted, not emulated (FLASH-CHIPS.md)); none of it can change in the shipped `fm1_web.wasm`.
- The chip-profile engine hash is verified for one toolchain (rustc 1.97.1, Windows). Another toolchain builds a working engine with a different hash; the build script says so and still checks the exports.
- The flash-ID patch works only on the exact engine build validated; a rebuilt `fm1_web.wasm` must be re-validated first.
- Machine, chip-model and chip-engine tests have been verified on Windows only (Node 24.19.0; Node 20.20.2 for the earlier tiers, not re-run for Stage C). macOS and Linux are unverified; the quick tier gates releases through `npm test`. Slow CI machines could approach the quick tier's 20 s limit (about 5 s here).
- The chip model rests on two datasheets (Puya V1.7, UC25HQ80 v1.2); other revisions may differ. Typical timings are "not 100% tested"; no minimum timing exists in either document.
- Boot ROM/loader are not emulated, so true bricking cannot be reproduced (TESTING.md known limitations).
