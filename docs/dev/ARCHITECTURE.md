# Architecture (verified findings)

Evidence tags: **[V]** verified in source or by running it; **[U]** uncertain.

## The app
- Electron shell (`main.js`, `preload.js`, `updater.js`) serves `site/` over `fm1://app` and loads `site/emulator/index.html` **[V]**. Windows-only extras: USB check/repair, bundled `vendor/M-Flasher`.
- Page (`site/emulator/*.js`, about 75 plain scripts sharing `window.FM1`, no bundler) **[V]**.
- Engine: `site/emulator/fm1_web.wasm` (2.6 MB), Rust compiled to WebAssembly (the **Default** engine; a second, **unified** engine `fm1_web_unified.wasm` runs the chip test modes: see "Unified engine and the chip test modes" below). Exports about 60 `fm1_*` / `panel_*` functions; imports only `env.fm1_jit_compile` **[V]**.
- The page loads the same wasm twice: once as a drawing library (`panel_draw` paints the front panel), once in the audio path (worker `engine.js` -> `stream-worklet.js`; fallback `worklet.js`) **[V]**.
- Firmware: `.fwsc` packages (JieLi UFW/JLFS format, parsed in `fwsc.js`); catalog `site/emulator/firmwares.json`; booted via `fm1_boot_fwsc` plus `package-resources.js` **[V]**.
- Audio: firmware computes the sound on the emulated CPU; the engine hands out 44.1 kHz float frames (`fm1_out_l/r`) **[V]**.

## Emulated hardware (upstream source, MIT, `joakimeriksson/fm1-emu`)
- Two pi32v2 cores (JieLi AC791N), timers, interrupts, LCD 240x240, key matrix, encoders, MIDI, USB (limited), watchdog and chip reset, XIP + SFC decrypt **[V]**.
- SPI flash model `crates/fm1-soc/src/spiflash.rs`: 1 MiB; commands 9F (ID), 4B, 05/35, 06/04, 03/0B, 20, D8, 02. Default ID `85 60 14`; SMK-37 board sets `EB 60 14` (`lib.rs:736`). Instant erase/program, never busy, no chip erase/SFDP/quad, program does not check write-enable, no page wrap **[V]**.
- Native-only power cut: `FM1_FLASH_CUT=N` (environment variable, cannot work in wasm) **[V]**.

## Fork engine vs upstream
- The fork's wasm contains the path `crates\fm1-soc\src\spiflash.rs` **[V]**, but is **not** a build of upstream master: it lacks `fm1_cpu1_fault`, `fm1_cpu1_survives`, `fm1_lcd_timed`, `fm1_jit_selftest` and has extras (`fm1_usb_plug`, `fm1_audio_in`, `fm1_skin`, `fm1_has_usr`, ...) **[V]**. The author's public repos contain no engine source; `tools/sync-emulator-mirror.ps1` mentions a private repo **[V]**.
- Therefore never assume upstream is a drop-in replacement.
- Stage B (2026-11-13) built upstream v0.3.0 (commit `631b790`) separately and compared it in lockstep with the shipped engine (USB off for both: v0.3.0 has no `fm1_usb_plug`): every compared observable matched in 51 of 51 runs, with one reproducible difference outside those observables, the **XIP-tail difference**: 3,488 of the 585,728 bytes of the decoded XIP window differ, at flash offsets `0x9225B-0x93000`; the shipped engine shows erased bytes there as `0xFF`, v0.3.0 shows scrambled-looking values; present at boot for every firmware, no behavioural difference seen; **cause not investigated**. The shipped engine is therefore *not* byte-for-byte reproducible from public source; v0.3.0 is only a behavioural reference.

## Flash-chip structure in the fork's engine memory (validated 2026-11-13, engine sha256 `cdf039104a74...0278`)
- The engine keeps **3 copies** of its flash-chip structure in linear memory **[V]**. Each starts with a pointer to the flash bytes (`fm1_flash()`) and holds the 3 JEDEC ID bytes **48 bytes after that pointer**. The same offsets in all 3; identical across the 6 firmware checked.
- **One copy is live, two are stale** leftovers (probably from Rust moving the structure; the cause is not verified). Absolute addresses depend on the heap, so never hard-code them. Liveness is proven at runtime: the live copy has the revision word at **+36**; writing a sentinel there makes the engine's own `fm1_flash_revision()` return it (note: the export returns a signed i32; compare unsigned) **[V]**.
- Patching only the stale copies changes nothing; patching only the live copy equals patching all three **[V]** (selftest). Changing the live ID changes firmware behaviour: `quadro-fm1` stops writing flash on `B3 60 14`, AURORA's screen changes **[V]**.
- The firmware's behaviour on the new ID is consistent with `docs/Recovery.md` (older firmware keeps saves in RAM on the newer chip). The chip's other behaviour is unchanged: ID selection is not chip emulation **[V]**.
- Layout is build-specific; `engine.mjs` `FLASH_ID_LAYOUTS` lists validated hashes. A different engine build is refused.

## Headless harness (`ci/machine/`)
```
cli.mjs / selftest.mjs
  monitor.mjs  (watch -> verdict)    flash.mjs (records, diff, corrupt)
  machine.mjs  (Fm1Machine)          engine.mjs (loads wasm, capabilities)
  fm1_web.wasm, read-only
```
- Capabilities come from the engine's exports; a test needing a missing one throws (`requires()`).
- Flash record format = engine restore format = app save format: 4-byte LE offset + 4096 bytes. Restore works only before the first render **[V]**.
- Two clocks: `audioMs` (harness) and `emulatedMs` (engine, runs ahead through idle skipping) **[V]**.
- `flashid.mjs` (Component 2): `parseFlashId`, `locateLiveFlashId` (finds candidates from the flash pointer, proves the live one, refuses on any mismatch), `applyFlashId`, `readFlashId`. Used by `Fm1Machine.boot({ flashId })`, `machine.flashId()`, `powerCycle()` (the choice persists) and the CLI `--flash-id`. FM-1 board only, before the first instruction runs.

## Chip-profile engine (Component 4 Stage C; `ci/engine/`)
```
ci/engine/build.mjs  pinned upstream v0.3.0 (git objects) + chip-profiles.patch + tables generated from ci/machine/chipspec.mjs
                     -> ci/engine/out/fm1_web_chips.wasm  (git-ignored, never committed)   verified against pin.json
engine: fm1-soc/src/spichip.rs (byte-stream chip state machine)  <- spiflash.rs routes to it only when a profile is selected
harness: flashchip.mjs (options)  machine.mjs (boot: select before the first instruction)  engine.mjs (capabilities)  cli.mjs
```
- **Where the flash lives:** `SpiFlash` in `fm1-soc/src/spiflash.rs`, reached only through the SoC's SPI0 registers (`0x11C00`) and chip select, which is GPIO PD0 (`lib.rs`: `flash.set_cs`, `flash.write`). With no profile selected the original code runs, unchanged.
- **Time (C0 finding):** the chip uses the SoC cycle counter `Periph::cycles` (at `Periph::hz`), the same counter that drives TIMER4's 24 MHz count (what AURORA's `took_us` reads), USB frames and the SMK-37's SPI1 busy. `Soc` hands the flash the cycle count before each chip-select and SPI0 write (`SpiFlash::set_clock`). Idle skipping only moves the counter forward, to just before the next event, so a deadline compared with `cycles >= end` is never missed; SPI0 is not a "pure read" for the polling-loop skipper, so a loop polling flash is never skipped and a WIP poll sees real emulated time pass (one cycle per instruction). Durations are the datasheet figures rounded up to whole cycles.
- **Chip state machine:** WIP/WEL/BP/SRP/QE/LB/CMP, protection tables, page wrap and last-256 rule, erases `20h 52h D8h 81h 60h C7h`, `9Fh 05h 35h 03h 0Bh 06h 04h 01h 02h`. It is a port of the Stage A model, replayed against oracle transcripts (388 scenarios, 85,283 transactions; see TESTING.md). SPI0 moves whole bytes, so CS rising mid-byte cannot occur on the machine; those cases are exercised through the chip API only. Unspecified behaviour is never guessed: the command is ignored with no state change and counted (`fm1_flash_events`); opcodes outside the model (such as `4Bh`) return `FF` and are counted.
- **Simplification (D33): array at accept.** The array changes when a program/erase command is accepted (CS rises), as in the original model, while WIP and WEL follow the cycle time. The datasheets leave array contents during a cycle unspecified; array reads during a cycle return `FF`. `changed`/`revision` and the XIP mirror therefore update at accept, exactly as before. Power loss during a cycle is Component 5. `FM1_FLASH_CUT` (native only) is not honoured under a profile.
- **Power cycle (C3):** the non-volatile status bits (BP4-BP0, CMP, SRP0, QE, LB3-1) are carried to the new machine for the same chip profile (`fm1_flash_nv_status` returns `value | unknown << 16`, `fm1_flash_nv_restore` applies the power-up rules: WEL clear, SRP1:SRP0 = 1:0 back to 0:0); a different chip swapped in starts at status 0. A write-status cycle still running at power-off is treated as completing (power loss mid-cycle is Component 5).
- **Exports** (the shipped engine has none of them): `fm1_flash_chip(id)` (0 original, 1 Puya, 2 UC25HQ80), `fm1_flash_timing(0 typical | 1 maximum)`, `fm1_flash_wip()` (the status register's WIP bit, **separate** from the unchanged `fm1_flash_busy()`, which stays chip-select), `fm1_flash_events(0 unspecified | 1 not modelled | 2 last not-modelled opcode)`, `fm1_flash_nv_status()`, `fm1_flash_nv_restore(v)`, `fm1_flash_uid_set(w0..w3)`, `fm1_flash_uid_clear()` (the 4Bh unique-ID fixture; `fm1_flash_events(3)` counts 4Bh reads answered without one), and four **test-only hooks** `fm1_test_bus_write32/read32`, `fm1_test_advance_us`, `fm1_test_set_wp` (drive SPI0, chip select, the cycle counter and WP# without firmware; `ci/machine/chiplive.mjs`). The unpatched v0.3.0 has 48 exports; the patched build 60.
- **No USB host:** v0.3.0 has no `fm1_usb_plug`; `usb: true` does nothing on this engine.

## Fault injection in the harness (Component 5, Stage 5D; `ci/machine/fault.mjs`, `faultscenario.mjs`, `faultpolicy.mjs`, `Fm1Machine`)
```
engine fm1_fault_* exports (Rust: chip journal + indeterminate list, SoC event, terminal power_cut) -> fault.mjs (encode, arm, read state/record/list, carry the list)
  -> Fm1Machine (status: running | halted | power_cut; run() stops at once; powerCycle({ outcome }))  -> monitor.mjs watch(): verdict power-cut
  -> faultscenario.mjs runFaultScenario(): deterministic JSON report            faultpolicy.mjs: explicit synthetic outcomes (never in the engine)
```
- **Survey (Stage 5E):** `faultsurvey.mjs` plans, shards and summarises scenarios over the firmware survey's 17 firmware and both chip profiles; harness-issued cycles (`inject`) cover the kinds no firmware issues; results: `docs/dev/fault-survey.json`, `FAULT-SURVEY.md`. An emulator trap (a Rust panic in the engine) is the verdict `engine-trap`, not a firmware result; the known one (D-1: an all-zero flash, or a 32-bit access at the edge of RAM) is fixed in the chip-profile engine (the patch also carries the SoC bus word-access fix, D80) and still present in the shipped one.
- Three stop states stay distinct everywhere (`fm1_halted` vs `fm1_power_cut`); the indeterminate list lives in the engine only and is carried into a rebooted machine by `fm1_fault_set_ranges`.
- The engine records interruption, affected range and indeterminate state; any outcome is an explicit named policy applied by the caller at the reboot (docs/dev/FAULT-INJECTION.md section 13).

## Flash-chip reference model (Component 4 Stage A; `ci/machine/chipspec.mjs`, `chipmodel.mjs`, `chiptests.mjs`)
```
chipspec.mjs   datasheet data: profiles (puya, uc25hq80), timing, block-protect tables, BEHAVIORS registry + citations
chipmodel.mjs  ChipModel: transact(tx, {read, partialBits}) -> {outcome, out, unknown}; readStatus(); peek(); powerCycle(); ManualClock
chiptests.mjs  87 conformance tests (expected values typed from the datasheets, incl. all 64 chip-erase combinations per profile and both printed protection tables) + traceability check
```
- **Not connected to the running engine** (the chip-profile engine is a Rust port checked against it; see above). Pure JS; one chip-select transaction at a time; time from a caller-supplied clock; completion at start + typical (or maximum) duration.
- Modelled: WREN/WRDI, RDSR (05h/35h, 16-bit status), WRSR, page program (wrap, last-256, AND), page/sector/32K/64K/chip erase, 9Fh, reads 03h/0Bh, BP/CMP/SRP protection, WEL/WIP rules, power cycle. Chip erase: Puya runs it when the table says nothing is protected (p.24, p.38); the UC25HQ80 refuses the 14 BP/CMP combinations where its p.9 and p.28 statements conflict. Everything else throws `NotModeled`; anything the datasheets leave open throws `UnspecifiedBehavior` or is flagged in the `unknown` mask (FLASH-CHIPS.md).
- Profile IDs equal the harness's selectable flash IDs (`flashid.mjs` FLASH_IDS), tested.

## Unified engine and the chip test modes (Component 8, Stage 2; 2026-11-16)

**Engines in the repository.** `site/emulator/fm1_web.wasm` (sha256 `cdf03910…`): the shipped engine, **unchanged**, the Default and the page's drawing instance (it alone has `fm1_skin`). `site/emulator/fm1_web_unified.wasm` (sha256 `5d595ae778bf8cf7c698c463ff175efa0a08313d1272efd30db7b34d3d74e0c8`, 2,747,410 bytes, 82 exports, imports only `env.fm1_jit_compile`): committed, runs the chip test modes. `ci/engine/out/fm1_web_chips.wasm` (`28dacdb4…`): the pinned chip-profile engine, still built on demand, still what the chip-engine tests use (D96).

**Provenance of the unified engine** (all in `ci/engine/`, pins in `pin.json` `unified`): upstream `joakimeriksson/fm1-emu` v0.3.0 (`631b790b191e87ea8b796d351cfe7e61ab366794`) trimmed to the four engine crates, + `chip-profiles.patch`, then `usb.rs` replaced **whole** by upstream commit `9acb2df464c7d91347f0c114423d955d909f4448` (blob `43af499a63d5d8d00169f38fc53df8ebe9900fae`), then `unified-engine.patch` (12 hunks): the PLL0 boot state (Stage 4, below), the shipped engine's four USB exports (`fm1_usb_plug`, `fm1_usb_conf`, `fm1_usb_conf_len`, `fm1_has_usr`), a USB audio-in host (`fm1_audio_in`, `fm1_audio_in_buf`, `fm1_audio_pending`, `fm1_has_audio_in`; the computer's audio into the device over isochronous OUT, no SET_INTERFACE sent: Stage 0 showed that matches the shipped engine's queue behaviour), and `fm1_xip_tail(mode)` (below). The build refuses unless `usb.rs` at `9acb2df` differs from v0.3.0's in exactly one line, the SPDX identifier (`GPL-3.0-only` to `MIT`). That replacement leaves the compiled binary byte-identical to the Stage 1 binary built with v0.3.0's `usb.rs` (a comment line; same line count): the Stage 1 validation applies by identity, and the pipeline's own rebuild reproduced it. **Not used:** the v0.4.0 or later `usb.rs` (about 440 lines of behaviour change; not a drop-in).

**What Stage 0/1 measured** (scratch, reported at the time; the committed tests below re-check a subset): shipped engine vs a v0.3.0 build with the USB exports over 277 packages, USB plugged, interpreter, 3 s: identical in display, audio, clock, flash and USB descriptor once the XIP tail is matched (275 of 277 before, the two differences being exactly the XIP tail); JIT 60 of 60; both chip profiles identical to the pinned chip engine (120 and 60 runs); audio-in queue traces 8 of 8; Rust tests 174 passed, 0 failed, 2 ignored. **The XIP-tail difference is explained:** the shipped engine decrypts only the app area and leaves the bytes after it as stored; v0.3.0 and every newer upstream also decrypt up to the protected image's end. `fm1_xip_tail(0)` (default) = shipped, `(1)` = v0.3.0; the 3,488-byte difference and the two firmware (`dx747`, `clatter`) that read it are exactly that. Which one is right for hardware is unknown.

**How the application uses it.** `site/emulator/chipmode.js` (modes, `applyChipProfile`, `chipStatus`, report text), `chipcompare.js` + `chipcompare-worker.js` (headless comparison), `chiptest.js` (the panel), plus small changes in `main.js`, `worklet.js`, `engine.js`, `index.html`, `style.css`:
- Default boots the page's own copy of the shipped engine exactly as before. A test mode makes `main.js` fetch `fm1_web_unified.wasm` on first use and send its bytes in the boot message (`engineId`, `chip`, `chipTiming`); `worklet.js` compiles one module per engine id and, after `fm1_boot_fwsc`, the resource laying, the flash restore and the USB host, calls `fm1_flash_chip` / `fm1_flash_timing` before the first instruction (the harness's own order). The page's drawing instance stays the shipped engine in every mode.
- A test mode is **ephemeral**: `boot()` passes no saved sectors, `saveSnapshot()` returns before touching `memoryRecords` or the save store, a session never forces a save. The saved patches of every firmware are therefore untouched by a test run (verified in the browser: the saved records were identical before, during and after a Puya session of quadro-fm1, which writes its settings). The selected mode is not remembered across launches (`?mode=old|new|puya|uc25hq80|original` selects one); the app always starts in Default.
- *Copy report* asks the running worker for `chipStatus` (`chip-status` message), takes a fresh flash snapshot in a test session, and builds the text with `chipmode.js buildReport`; it also shows the text in the panel in case the clipboard is refused. *Compare chips…* runs `chipcompare.js runComparison` in a worker: the original engine, then the unified engine under the Puya and UC25HQ80 profiles, each a fresh machine, 3 emulated seconds, interpreter, USB plugged, **no key presses**; it records halt, first screen content, audio level, screen hash, changed flash sectors, WIP seen and the chip's ignored/unmodelled counters, and states differences. The cause of a difference (for example a JEDEC ID check) is only ever given as a labelled inference.

**Host interfaces kept.** The JIT host interface is the v0.3.0 one (`fm1_jit_compile(ptr, len)`, region modules import the function table) in `jit.js`, `worklet.js` and the harness, for both engines. The 45 export names the page, worker and worklet use are all present in both engines except `fm1_skin` (drawing instance only). USB audio in, USB, the LCD, audio and MIDI paths in the worklet are unchanged.

**Limits.** FM-1 board only in chip modes; no fault injection, flash-ID or unique-ID control in the application (the engine has the exports; the harness and CLI keep using them); no claim that either profile matches a physical chip.

### PLL0 boot state in the unified engine (Component 8, Stage 4; 2026-11-16)
**What:** `Soc::new` sets `0x119a0` := `0x4540_0203` and `0x119a4` := `0x3f50_3026` (constants `PLL0_CON0`, `PLL0_CON1`, `PLL0_BOOT`) after the struct is built, in that order, via `sfr_set`. Source: upstream fm1-emu `d2bcc331d039855060dcef78c3bcaebb193b213a` (2026-11-07; first in v0.5.0), taken verbatim; its test (plus a whole-word read and four neighbouring words that stay 0) is `tests::pll0_reads_as_the_bootloader_left_it`. It is one hunk group in `ci/engine/unified-engine.patch` on the v0.3.0 base; no newer upstream file was imported.
**Why:** felucca-bsp's audio driver checks the audio PLL before starting ALNK0 and leaves the audio off under any other clock; the engine started every analog register at 0, so firmware built on that driver drew its screen and never started audio.
**Effect, measured (Stage 3 scratch build and the committed Stage 4 engine, 277 packages, interpreter, 3 s, USB on, original flash model, against the shipped engine):** 262 identical, 15 differ and nothing else: `amb`, `amenity`, `assid`, `atek303`, `choppah`, `ctl`, `fm1-ripple`, `fmfam`, `krisjangle`, `loom`, `midimon`, `mutable`, `polly`, `remotefm1`, `sidou`. In all 15 the emulated clock now follows the audio (for example `amb` 14,242 ms to 1,270 ms per audio second, `ctl` 57,847 ms to 1,269 ms) instead of fast-forwarding; `amb`, `mutable` and `sidou` are audible within the 3 s with no key pressed; for the other 12 no output was seen in 3 s without input (not tested with input). Four of them (`fmfam`, `remotefm1`, `ctl`, `midimon`) also write flash differently because they now run on. Upstream's own list for the change names AMB-1 1.3.2, CTL-1 1.0.3, CHOPPAH 0.99 and Polly 0.6.2: `amb`, `ctl`, `choppah`, `polly` are among the 15.
**Consequences:** (1) the unified engine with the original flash model is **no longer identical** to the Default for those 15 packages; the Stage 1 "277 of 277" now reads 262 of 277, the remaining 15 being exactly this change. Differences **between** the chip modes are unaffected (same engine). (2) The **shipped Default is unchanged**: it still starts those firmware without audio. (3) **Unverified:** upstream attributes the values to reads off real FM-1s; this project has not checked them on hardware, so they are not hardware truth here, and no claim is made about which real units or firmware revisions they match. The in-app report states this for every test mode (Stage 6 reworded it in plain language and added a per-package note and a panel notice, below).

### PLL0 clarification and the four-row comparison in the application (Component 8, Stage 6; 2026-11-16)
**The list.** `site/emulator/pll0-firmware.json` names, **by package SHA-256 only**, the 15 bundled packages whose audio engine starts on the unified engine and never on the shipped Default (`amb`, `amenity`, `assid`, `atek303`, `choppah`, `ctl`, `fm1-ripple`, `fmfam`, `krisjangle`, `loom`, `midimon`, `mutable`, `polly`, `remotefm1`, `sidou`). It is evidence-based like `ci/boot-quarantine.json` and is the only classification used: `classify.json` covers 187 of 277 packages and 7 of these 15 and has no audio-clock field (Stage 5), and an id or a name is never compared (another version of a firmware may behave differently). Each entry carries the catalogue's name and version, the package hash and the frame counts measured on both engines; the file also records the unified engine's sha256, so a rebuilt engine invalidates it until `node ci/pll0-audit.mjs --check` (all 277 packages on both engines, about 9 minutes; `--write` regenerates) is run and the result reviewed.
**The metric: "audio engine started".** The frames `fm1_render` returns as real audio (the firmware's I2S DMA delivered them), summed over a run, greater than 0. It is measured the same way in every compared mode (the page's own render loop). The evidence over all 277 packages (2 s of audio time, both engines): the audio-started status differs between the two engines for exactly these 15 (shipped 0 real frames, unified 86,656 to 88,320 of 88,320), for the other 262 the frame counts are identical on both engines (258 start on both; `lsdjburrito`, `transitfm1`, `fm1-mocky`, `trireme-fm1` start on neither). The emulated-clock to audio-clock ratio was **rejected** as the metric: it separates the 15 in the Stage 3/4 runs (14 to 64 on the shipped engine, 1.1 to 2.3 on the unified) but unaffected packages reach 34 on both engines (`picovave`, idle skipping), so it would mislabel them. Starting the audio engine is **not** audibility: the 12 packages of Stage 5 need input, and 3 stayed silent in everything tried.
**The notice (panel).** `chipmode.js` `pll0Entry(sha256, data)` (hash only) and `panelNotice({ mode, entry })`: shown under the mode note only in a **test mode** and only when the loaded firmware's package hash is on the list (the booted package's hash; before a boot the catalogue's sha256 for the selected firmware; a firmware opened from a file is matched by its own hash). Text: it may start its audio on the test engine while Default stays silent because the two engines set up the audio clock (PLL0) differently; it may still make no sound until played, and not every firmware does; the PLL0 values come from the upstream emulator and have not been verified on a physical FM-1; compare chips against "Original flash model on the unified engine", not against Default. Verified in the browser: hidden in Default and for unlisted firmware (`felucca`), shown in all three test modes for `ctl` and `amb`, hidden for a copy of the CTL-1 package with one byte changed (a different hash, the same name).
**The report.** Every unified-engine report carries a plain explanation of the engine's audio-clock initialisation with the not-verified-on-hardware caveat (replacing the jargon line of Stage 4); a matching package also gets a firmware note (in any mode): its audio engine starts on the unified engine and not on Default, that says nothing about audibility, and a difference from Default may come from the engine rather than only the flash chip.
**Compare chips.** Four rows: Default, **Original flash model on the unified engine**, Puya, UC25HQ80, with "audio engine: started / did NOT start (N real audio frames of M rendered)" as a statement of its own, apart from "audible output" and from flash. Differences are scoped: `[engine]` Default against the original flash model on the unified engine (nothing about the flash chip changes between them), `[chip]` each profile against that same-engine row, and the two profiles against each other (the JEDEC remark stays a labelled inference). A profile is never compared with Default, so a chip is named for a difference only when a same-engine pair shows it. Example (CTL-1, browser): the only difference is `[engine]` "audio engine started here but not in the reference"; with Default running no audio the CTL-1 comparison takes about a minute because the shipped engine fast-forwards.

## The experimental CPU-optimization mode (Stage 2 of the optimized engine; 2026-11-18)
`MODES` has a fifth entry, `adaptive-cpu` ("Adaptive CPU Optimization (Experimental)", engine key `optimized`, `test: true`, `experimental: true`, `settledLoop: true`). Choosing it reboots the firmware on `site/emulator/fm1_web_frodhes_optimized.wasm` (fetched once, on first use,
by the generic `engineBytesFor`); `main.js` adds `settledLoop: !!mode.settledLoop` to the boot message and `worklet.js` calls `applyExperimental(x, m.settledLoop === true)` after the flash restore, the USB plug and the chip profile. The optimization is off in every new boot of the engine, so every other mode
(and every reboot out of this one) runs without it. The worker caches its compiled module by engine id (`optimized` is distinct from `shipped` and `unified`). The mode is ephemeral because `test` is: `ephemeral = mode.test` in `main.js` already gates every read and write of the saved patches. Nothing about the mode or engine
is stored; `?mode=adaptive-cpu` (aliases `adaptive`, `optimized`) opens it and a new page load is always Default. This is a temporary validation switch: the intended product is the optimization in the normal execution path, with no mode and no engine choice. The Default engine (`fm1_web.wasm`) cannot be patched
(no public source, see Stage B above), so making the optimization part of Default means either obtaining that source or moving Default onto a unified-based engine, which changes 15 of 277 packages (PLL0 boot state): a Default-behaviour decision for the user.

### Making the optimization part of the normal execution path: the Default-engine issue (2026-11-18)
Facts [V]: Default runs `site/emulator/fm1_web.wasm`, a fork binary with no public source (Stage B, D2); the optimization is a patch on the unified engine's source (upstream v0.3.0 + this project's patches). The page also uses the shipped wasm for the panel drawing (`ui = instantiate(wasm)` in `main.js`), so that file stays in any case.
Options and what each costs in compatibility:
1. **Obtain the fork's source** and port `settled-loop.patch` (four files; the fork's `machine.rs`, `periph.rs` and core may differ). Default then keeps its exact behaviour (PLL0 registers at 0, its USB audio host) and gains the speed-up. Needs the source from its author: your participation.
2. **Move Default's machine engine onto the optimized unified engine** (optimization on by default inside the engine, no mode). Changes Default for the 15 PLL0 packages (their audio starts; evidence below suggests this is the hardware behaviour, not measured) and, when USB audio-in is streamed, for 6 packages (unarbitrated); the other 256 are identical in everything on the Stage 2 harness. Replaces the proprietary machine engine: explicit user approval required.
3. **Per-package engine selection** (shipped for the 262 identical, unified for the rest): rejected, it is a firmware-specific special case and keeps two engines.
4. **Binary-patching the shipped wasm**: not viable (no source, no way to prove equivalence).
PLL0 evidence [V unless noted]: all 15 listed packages contain `0x45400203` and `0x07503026` (the masked CON1 value) as constants in their own code (`audio-audit/stage2-validation/pll0scan.mjs`), none of the other 262 do; upstream's commit d2bcc33 states the BSP driver rejects any other PLL0 value and that M-VAVE's bootloader and m-bootloader leave these values (read off FM-1s). A firmware that ships working on real units must therefore see these values there; Default's all-zero analog registers are the deviation for those 15. Not measured on a physical FM-1 [H]: a user check that e.g. AMB-1 or CTL-1 makes sound on a real unit would confirm it.

### The XIP tail is decrypted by default in the unified engine (2026-11-18, D108)
Facts [V]: the shipped engine decrypts only the app area of a package's XIP image and leaves the bytes after it as stored; upstream v0.3.0 and newer decrypt up to the protected image's end (`fm1_xip_tail(0|1)`, D96). The decoded window differs between the two modes for all 277 catalogue packages (269 by the same 3,488 bytes at the end of the window; 8 by other spans); the official stock `FM-1.fwsc` (sha256 `d017fb65...61d5`, from M-VAVE) has a larger one (3,971 bytes). Almost every firmware never reads the region.
**Stock firmware.** It keeps a small encrypted table entry (an `EXT_RESERVED` marker, the same entry `dx747` and `clatter` have) at the end of the app area. With the tail as stored (the shipped engine and unified mode 0) it never starts its audio engine: black screen, no audio frames, the CPU about 94% idle, identical on the shipped engine, the unified engine and v5 on or off. With the tail decrypted (the chip-profile engine, unified mode 1) it starts audio at about 0.6 s of emulated time and draws its status bar; writing the decrypted bytes into the shipped engine's window at harness level also starts it and writing the stored bytes into the chip engine's stops it (cause established). The firmware runs on real units, so the hardware reads that entry decoded.
**`dx747` and `clatter`** (`dx747-0.1.fwsc` sha256 `91f9acd0...0934`, `clatter-1.0.0.fwsc` sha256 `4d661dae...5956`; the only two of the 277 whose behaviour differs, as in Stage 0/1; 6 s, JIT on, USB plugged, input script, tail off against on): each writes a 33-byte record at the start of the sector after its image (`0x7203F`-`0x72064` and `0x7303F`-`0x73064`) that differs between the modes (same write times, no halt). `dx747`: audio differs from about 2.65 s (9,849 of 260,480 samples; RMS 0.0618 in both), screen identical. `clatter`: audio differs from about 4.92 s (43,867 of 260,864 samples; RMS 0.0429 against 0.0428), screen differs in 3 of 13 samples. Seven other packages checked (`smileyface`, `xmod`, `pigeon`, `picovave`, `playa`, `jiant`, `rhythmer`) are identical in audio, screen and flash. **Which output is right for those two is not known**; they are a documented compatibility change of the unified engine against the shipped engine, not a defect found. The stock firmware shows that the hardware decodes at least the table entry; it does not show what the hardware returns for the erased bytes after it (a decrypting reader would return noise there, as mode 1 does).
**Change:** `XIP_TAIL_DECRYPT` starts true in `unified-engine.patch`; `fm1_xip_tail(0)` selects the old behaviour. New unified engine `5d595ae778bf8cf7c698c463ff175efa0a08313d1272efd30db7b34d3d74e0c8` (2,747,410 bytes) and optimized engine `20e5300c5714a4b70ebabc4b49b43d1ae8062a8ac1c9eee272aee8d6e82edd9a` (2,799,146 bytes), both rebuilt by `ci/engine/build.mjs --optimized` from the pinned sources; the chip-profile engine (`28dacdb4...`) and the shipped engine (`cdf03910...`) are unchanged. Evidence: `audio-audit/xip-tail/` (outside the repository).

### Final engine architecture (2026-11-18, D109)
- **Default** runs `site/emulator/fm1_web_frodhes_optimized.wasm` (unified engine + `settled-loop.patch`, `20e5300c...`) in the worker (`engine.js` -> `worklet.js`). The worklet switches the CPU optimization on after every Default boot (`m.settledLoop` from the mode; `fm1_settled_loop(1)`); the engine's switch is off in every other boot. The original flash model, XIP tail decrypted (D108), the USB host and USB audio-in come with the engine. Default is the only mode that reads and writes saved patches (flash sectors restore through `fm1_flash_restore`, which the unified engine has).
- **The shipped `fm1_web.wasm`** (`cdf03910...`, unchanged) is fetched by the page for two things: it draws the front panel in every mode (`fm1_skin`, only it has it) and it runs the *Previous engine* test mode. It no longer runs firmware in Default.
- **Diagnostic modes** (Flash chip test panel, all ephemeral): Puya and UC25HQ80 profiles run the optimized engine with the CPU optimization on, like Default (validated on all 277 packages under both chips, D129); *Original flash model on the unified engine, no CPU optimization* runs `fm1_web_unified.wasm` (`5d595ae7...`); *Previous engine* runs the shipped engine; Compare chips runs four configurations (previous engine, unified original model, Puya, UC25HQ80); the first two are controls that feed the verdict, and the report lists only the two chip rows and the differences between them. Nothing about the mode, engine or optimization is stored (guarded by `ci/chip-mode-tests.mjs`).
- **Known differences from the previous engine** (not decided, documented): 15 PLL0 packages start their audio on the new engine; six audio-in packages differ when USB audio is streamed; `dx747` and `clatter` differ through the decrypted XIP tail (D108); the official stock `FM-1.fwsc` boots (it did not) but its sound generation and complete UI are unverified and it runs at about 0.1x real time at 60-100 MHz (the optimization skips nothing for it: core 1 is busy). Real audio device, packaged Electron and physical hardware are untested.
