# Decisions

| ID | Date | Decision | Why |
|---|---|---|---|
| D1 | 2026-11-13 | Fork cloned to `FM1\fm1-emulator`; `origin` = HEATWAVS fork, `upstream` = briksquared | User request |
| D2 | 2026-11-13 | Do **not** replace or merge the upstream engine. Build it separately if needed and compare | The fork's wasm has exports upstream lacks and is not a known build of public source |
| D3 | 2026-11-13 | Harness is new files only under `ci/machine/`; no existing file edited | Keep the original emulator working; easy to review/revert |
| D4 | 2026-11-13 | Interpreter (no JIT) is the harness default | JIT is opt-in in the app (can stall audio); determinism verified only for the interpreter |
| D5 | 2026-11-13 | Verdicts: `booted`, `crashed`, `blank`, `display-lost`. No `hung` verdict | A static screen waiting for input looks the same as a stuck loop; needs a stimulus per firmware |
| D6 | 2026-11-13 | Engine capabilities are detected from exports; unsupported features throw instead of passing | Never claim a test passed by silently skipping it |
| D7 | 2026-11-13 | Missing-feature behaviour is locked in by `KNOWN LIMITATION` tests | If an engine starts modelling boot/key areas, tests fail and flag new test options |
| D8 | 2026-11-13 | Commits stay local; push only on request | User instruction |
| D9 | 2026-11-13 | Project docs live in `docs/dev/`, separate from user-facing docs in `docs/` | Avoid touching existing documentation |
| D10 | 2026-11-13 | Flash ID is selected by a **runtime patch** of the live chip structure in engine memory, not a Rust rebuild; `fm1_web.wasm` is never modified | Cheapest verified route; the engine binary stays byte-identical; the native export moves to Component 5 |
| D11 | 2026-11-13 | Component 2 is **ID selection only**: no timing, extra commands, fault injection or recovery | User scope. Only the bytes of the JEDEC read (`0x9F`) change; chip emulation fidelity is Components 4 and 6 |
| D12 | 2026-11-13 | Patch only an engine whose sha256 is in `FLASH_ID_LAYOUTS`; anything else is refused | The memory layout is build-specific |
| D13 | 2026-11-13 | The live copy is **proven** (engine's own `fm1_flash_revision` echoes a sentinel) and only it is patched; exactly the validated number of copies and exactly one live copy, else refuse and leave memory untouched | User condition 3-4; blind patching of all copies is not justified by evidence alone |
| D14 | 2026-11-13 | Selectable IDs: `puya` (`85 60 14`) and `uc25hq80` (`B3 60 14`) only; FM-1 board only (not the SMK-37's `EB 60 14`); only at boot | Scope; arbitrary IDs would also defeat the locator's known-ID check |
| D15 | 2026-11-13 | Plan order revised: selectable ID is Component 2; `npm test` hook is Component 3; Rust build Component 5 | Evidence from the runtime-patch investigation |
| D16 | 2026-11-13 | Machine self-test has two tiers: **quick** (19 harness tests when decided, ~5 s, tagged `test.quick`; 89 with the chip-model tests, D28) runs inside `npm test`; **full** (all 30, ~90 s) is `npm run test:machine`. The full tier runs every test, so quick is a subset by construction | Keep `npm test` fast (8 s -> ~13 s) so it keeps being run; keep the slow firmware-behaviour checks one command away |
| D17 | 2026-11-13 | `npm test` runs the quick tier with a hard 20 s timeout (`MACHINE_QUICK_LIMIT_MS` in `ci/verify.mjs`) and fails with a distinct "exceeded its 20-second limit" message | A stuck emulation must never hang `npm test` or a release build |
| D18 | 2026-11-13 | The full machine suite stays at the original **30 tests**. The Component 2 test "default is untouched" is a single quick test whose function receives `{ full }`: its fast memory-identity check runs in both tiers, its slower whole-run comparison only in the full tier | User requirement (keep 30); the default-preservation guard is in the quick tier and no assertion is lost. (An earlier draft split it into two tests, making 31; reverted.) |
| D19 | 2026-11-13 | Real Felucca boot stays in the quick tier as the smoke test | User decision |
| D20 | 2026-11-13 | Full machine tier NOT added to CI yet | Only Windows is validated (Node 24 and Node 20.20.2); macOS/Linux first. The quick tier reaches CI via `npm test` regardless |
| D21 | 2026-11-13 | Component 4 is staged: **A** JS reference model and oracle (done), **B** isolated engine build, **C** Rust port, **D** harness integration. Plan renumbered (fault injection 5, scenario tests 6, boot area 7) | The shipped engine's chip behaviour cannot change; a specification first de-risks the port |
| D22 | 2026-11-13 | Stage A is JavaScript only: no Rust, no WASM change, not wired into the running emulator. It is a test oracle, not an improvement of emulated behaviour | User conditions |
| D23 | 2026-11-13 | Every modelled behaviour is a registry entry with a level (verified / interpretation / unspecified / not-modeled) and page-and-section citations per profile; a test fails if any lacks a citation or a test | Traceability requirement |
| D24 | 2026-11-13 | **Refuse to guess:** where the datasheets are silent or contradict themselves the model throws `UnspecifiedBehavior`; open status bits are reported in an `unknown` mask. Not-modelled features throw `NotModeled` | User condition: do not invent behaviour; uncertain cases are reported, not guessed |
| D25 | 2026-11-13 | Timing: **typical** is the default, **maximum** is a stress profile, **no minimum** (none printed); time comes from a caller-supplied deterministic clock, never real time | User decision |
| D26 | 2026-11-13 | The older chip's profile is the **Puya P25Q80H (V1.7)** documented reference only; the physical older FM-1's exact variant is unresolved and not claimed | User decision; evidence is the ID table match, not an inspected unit |
| D27 | 2026-11-13 | The two profiles are independent (separate literal tables, separate citations) even where identical; tests hold their own literal copies of the expected datasheet values, and a test compares the profiles where they differ | Each datasheet can be checked and corrected on its own; catches transcription errors |
| D28 | 2026-11-13 | The chip-model tests (70 when decided, 75 after D29) are registered in the machine self-test quick tier (quick 19 -> 94; full 30 -> 105). The 30 original tests are unchanged | Fast (milliseconds), runs in `npm test` |
| D29 | 2026-11-13 | **Chip erase:** Puya runs it exactly when the BP/CMP table says "None protected" (Puya V1.7 p.24, p.38; 14 of 64 combinations), with no refusals; the UC25HQ80 keeps refusing only the 14 combinations where its own p.9 and p.28 statements conflict. Tests state the expected outcome of all 64 combinations per profile as literal lists, add no-WREN tests for every write command, a chip-erase comparison of the profiles, and a literal copy of both printed protection tables | A final review found the model had applied the UC25HQ80 ambiguity to Puya; the Puya wording is unambiguous. Literal expectations avoid reusing the model's decision logic |
| D30 | 2026-11-13 | Stage B/C engine base is **upstream v0.3.0** (commit `631b790b191e87ea8b796d351cfe7e61ab366794`), built in a separate, never-committed test engine; the shipped `fm1_web.wasm` is not replaced | User approval (D4 of Stage C); v0.3.0 is a behavioural reference (51/51 runs matched), not a byte-identical source of the fork's engine |
| D31 | 2026-11-13 | The engine change is a **patch file plus a pinned, verified build script** (`ci/engine/`), not vendored crates and not a fork | Small and reviewable; source stays upstream's; build fails on any pin mismatch (patch hash, commit, tables, exports, toolchain hash) |
| D32 | 2026-11-13 | The Rust tables are **generated** from `ci/machine/chipspec.mjs` at build time and are not in the patch; `pin.json` records their sha256 | One source of truth for datasheet data; a spec change forces a deliberate rebuild and pin update (a quick test fails otherwise) |
| D33 | 2026-11-13 | **Array-at-accept:** under a chip profile the array changes when a program/erase is accepted; only WIP and WEL follow the cycle time | Datasheets leave array contents during a cycle unspecified; keeps `changed`/`revision`/XIP behaviour identical to the original. Mid-cycle power loss is Component 5 |
| D34 | 2026-11-13 | Under a profile, opcodes outside the model (incl. `4Bh` unique ID) return `FF` and are counted; unspecified behaviour is ignored and counted, never guessed | Consistent with D24; the original model's invented `4Bh` pattern is not reproduced |
| D35 | 2026-11-13 | `flashChip`/`flashTiming` are chosen at boot, before the first instruction, and refused before booting if invalid or conflicting (`flashChip` + `flashId` = `id-conflict`; timing without a profile = `timing-needs-chip`); `legacy` is the default and calls nothing. `flashId` stays ID-only | User requirements; the default path must stay untouched |
| D36 | 2026-11-13 | The generated test engine is **never committed** (`ci/engine/out/` is git-ignored). Live chip tests are full-tier only and are reported SKIPPED, not passed, when it is absent | No large binary fixtures; never claim a skipped test passed |
| D37 | 2026-11-13 | The Rust oracle-replay tests are `#[ignore]` unless `FM1_CHIP_ORACLE` names a transcript; `build.mjs --test` generates it and runs them with `--include-ignored` | A plain `cargo test` of the patched tree shows them as ignored instead of failing |
| D38 | 2026-11-13 | The chip engine has no USB host (`fm1_usb_plug` is a fork addition); any comparison with the shipped engine must use `usb: false` on both | Found when a Felucca comparison with the default `usb: true` differed in LCD hash and idle time for that reason alone |
| D39 | 2026-11-13 | The chip engine gains **test-only bus hooks** (`fm1_test_bus_write32/read32`, `fm1_test_advance_us`, `fm1_test_set_wp`) so the live chip can be conformance-tested over SPI0 without firmware and with a controlled clock. They are in the separately built engine only, pinned in `pin.json`, documented as test-only | Live conformance needs a way to drive the chip; running firmware cannot give a controlled clock or arbitrary command sequences. The shipped `fm1_web.wasm` has none |
| D40 | 2026-11-13 | **Non-volatile status bits survive `powerCycle()`** for the same chip profile (new exports `fm1_flash_nv_status`/`fm1_flash_nv_restore`; WEL does not; SRP 1:0 returns to 0:0; a swapped chip starts fresh; a cycle running at power-off is treated as completing). Replaces the C2 limitation "status not carried" | Real chips keep BP/CMP/SRP0/QE/LB while off (datasheets), so a protection test across a power cycle must keep them. Mid-cycle loss stays Component 5 |
| D41 | 2026-11-13 | `fm1_flash_events(2)` reports the last opcode the model did not cover, so a refused opcode can be identified, not just counted | Needed to resolve the quadro-fm1 case (D42); no behaviour change |
| D42 | 2026-11-13 | **`4Bh` (Read Unique ID) stays "not modelled"**: Stage A cites it only in the commands listings (Puya p.20-21, UC25HQ80 p.13); its dedicated section was not read, so its response (dummy bytes, length) is not specified by the Stage A sources. The model answers `FF` and counts it; nothing is invented | Refuse to guess (D24). quadro-fm1 handles it (all-FF/all-0 = "no unique ID", falls back to the Bluetooth address) |
| D43 | 2026-11-13 | Live conformance expectations are the datasheets' literal values (printed protection and timing tables from `chiptests.mjs`), not read from `chipspec.mjs` or the Rust tables; the Stage A oracle is additionally replayed in full over the live engine (byte-aligned form of the transcripts) | Independent of the spec's own decisions; the replay covers what hand-written tests cannot enumerate |
| D44 | 2026-11-13 | **4Bh Read Unique ID is now modelled in the reference model** (`chipspec.mjs` `ruid.*`, `chipmodel.mjs` `#ruid`), from both datasheets' dedicated sections; each finding is labelled verified / interpretation / unspecified / unknown (FLASH-CHIPS.md). Supersedes D42 for the reference model only: the Rust engine still answers FF and the legacy profile keeps its `FM1-` pattern | Stage A extension approved after C4 showed 4Bh to be the one behaviour that changes firmware (quadro-fm1, fm1-field) |
| D45 | 2026-11-13 | The unique ID's **value** is a caller-supplied fixture (`ChipModel({ uid })`, 16 bytes in transmission order); without it the bytes are reported unknown (mask `FF`). The model never invents a value and never uses the `FM1-` pattern | The value is per device and in neither datasheet (D24) |
| D46 | 2026-11-13 | Dummy bytes: Puya's are read as don't-care (interpretation, as for 0Bh); the UC25HQ80's Table-7 lists `00H` for bytes 2-4, so non-zero values there are unspecified and refused; byte 5 is don't-care | Do not infer behaviour the tables do not state; the asymmetry is the datasheets' |
| D47 | 2026-11-13 | Default oracle transcripts never contain 4Bh until the engine implements it (`gen-transcripts.mjs --with-ruid` adds opt-in 4Bh scenarios for the port); `nm.unique-sfdp` stays the id for 5Ah. The live tests that assert the engine's present FF/"not modelled" answer for 4Bh (and the C4 firmware tests naming 4Bh) stay valid and must be revisited at the port | Keeps the Rust host replay and live replay (and the unchanged engine) consistent with the oracle |
| D48 | 2026-11-13 | **4Bh is implemented in the Rust chip engine** for both profiles, exactly as the reference model (D44-D46). The legacy profile's original `FM1-` answer is untouched | Approved engine port |
| D49 | 2026-11-13 | The unique-ID **fixture** is configured through `fm1_flash_uid_set(w0..w3)` / `fm1_flash_uid_clear()` (harness `flashUid`, CLI `--flash-uid`); it lives in the chip, survives power cycles and the status restore, is per chip profile (a swapped chip has none), and is never invented | The value is per device and in neither datasheet (D45) |
| D50 | 2026-11-13 | With **no fixture**, 4Bh answers `FF` and counts the read in `fm1_flash_events(3)` (`flashUidUnknownReads()`); it is neither an unspecified nor an unmodelled event. The oracle reports the same bytes as unknown (mask `FF`) | Keeps the firmware outcomes of C4 unchanged by default and makes the missing ID explicit. FF is not equivalent to the `FM1-` pattern |
| D51 | 2026-11-13 | The byte stream cannot express every oracle case: with CS# rising before the fourth dummy byte a later byte is a dummy slot, not data. The opt-in `--with-ruid` scenarios therefore use only shapes the stream can express (short commands with no data bytes) | Same limitation as for 0Bh/03h; the oracle keeps the full set, tested through the model |
| D52 | 2026-11-13 | The build's `--test` replays the `--with-ruid` transcripts (the default scenarios plus the four 4Bh ones) through the Rust chip API and the SoC registers; the live replay does the same over the engine. Engine-answer tests that asserted FF/"not modelled" for 4Bh were rewritten for the port | One transcript, three implementations (model, Rust, live engine) |
| D53 | 2026-11-13 | Stage 5B scope: JavaScript only (spec, reference model, policy functions). Operations in scope: page program, sector/32 KiB/64 KiB block erase, chip erase. **Out of scope and refused, never silently completed:** WRSR, page erase 81h, suspend/resume, reset during a cycle, brown-out | Approved narrowing of the 5A design (decision 3); each excluded item needs its own proposal |
| D54 | 2026-11-13 | The reference model never takes an outcome policy and never states post-interruption contents: it records interruption, range and indeterminate state, exposes `before`/`ifCompleted` as policy inputs, and `peek` throws `UnspecifiedBehavior` over indeterminate bytes. Synthetic fills live in `faultpolicy.mjs`, which has no model access; a test checks the separation | Physical uncertainty stays separate from synthetic outcomes; a synthetic fill must never look like a datasheet fact |
| D55 | 2026-11-13 | An explicit outcome policy (and an explicit seed for seeded fills) is mandatory; there is no default fill. Every outcome is labelled synthetic and carries the standing disclaimer; `standardSweep()` is `exhaustive: false` | Replaces 5A decision 1 as approved; avoids a silent default being read as a prediction |
| D56 | 2026-11-13 | Cut precedence: a scheduled cut fires before normal completion at the model's single choke point `#settle()`, which every entry point (including `faultState()`) runs first. Lazy detection at the next SPI access is not enough on its own; for the engine this is a 5C proof obligation (scheduled deadline in the SoC's next-event computation, recommended) | Overrides 5A decision 2 (lazy detection); the harness reads the array directly, so a pending cut must not be bypassable by not touching the chip |
| D57 | 2026-11-13 | Determinism: same flash, profile, timing, trigger, policy and seed give identical records and bytes. PRNG mulberry32, one draw per record byte (top byte), draws independent of unknown bytes, vectors frozen from an independent implementation. `prefix(f)` = first `floor(f*n)` bytes new, rest old | Reproducible failure tests; independent vectors guard against a self-confirming PRNG |
| D58 | 2026-11-13 | Fault injection disabled means unchanged: the oracle transcript hashes are pinned in a full-tier test and an armed-but-never-matching or disarmed trigger is shown equal to no trigger | Requirement 5; the 87 earlier model tests are unchanged and still pass |
| D59 | 2026-11-13 | **Approved design (5C); 5C-1 implements only the chip part, the scheduling and sync points are 5C-2:** a power cut is a scheduled event in the SoC's own event machinery (`Periph::next_event`, new `flash_cut_at`), fired at its cycle, so XIP/JIT/idle-skip/loop-skip/harness observation see it at the right time; the chip's `settle()` also never lets completion win over a due cut; a sync runs at every clock-moving export's return and at the core-1 slice boundary. Lazy detection at SPI access alone is rejected | Requirement 1 for the engine; the investigation (FAULT-INJECTION.md section 9) found lazy detection cannot cover XIP data/code reads or harness reads |
| D60 | 2026-11-13 | **Approved design (5C), implemented in 5C-1 (chip part):** after a cut the bytes of the range hold the pre-image only as a labelled placeholder; the engine's indeterminate list is the authority and survives any fill; the harness applies explicit synthetic bytes from `faultpolicy.mjs`; the engine never computes a fill; reads of listed bytes are counted; the cut is terminal for the machine (`power_cut`, never `halted`) | Keeps physical uncertainty separate from synthetic outcomes in the engine (requirements 2, 4) |
| D61 | 2026-11-13 | 5C-1: the Rust chip captures the pre-image of the affected range **at accept** (before the array changes, D33) and what a normal completion would produce (right after), only while journaling is on (`arm_fault` or `set_fault_injection`); a cut keeps both as inputs, marks the ranges indeterminate and never computes an outcome. `sync_cut` writes the pre-image back as a labelled placeholder; there is no fill in the engine | Requirements 2-4 of 5C-1: pre-image preserved, indeterminate tracked beside the array, fills stay harness policies |
| D62 | 2026-11-13 | 5C-1 deliberate differences from the model: times in cycles with the cut clamped before the end; a powered-off chip answers `0xFF` and counts instead of throwing; `power_cut()` refuses (`fault.not-enabled`) a cycle accepted before journaling was on; `power_cycle()` after a cut is ignored and counted; reads of indeterminate bytes return the array byte and are counted | The engine has no exceptions and a byte stream, and must not fake a journal it did not take |
| D63 | 2026-11-13 | The model is the oracle for the chip state: `gen-transcripts.mjs --with-fault` (opt-in; default transcripts byte-identical, pinned) adds 296 interrupted-operation scenarios; the Rust chip driver replays them (3,220 fault steps, 0 mismatches); the register driver skips them until 5C-2. `build.mjs --test` passes the flag | One transcript, two implementations, as for 4Bh (D52) |
