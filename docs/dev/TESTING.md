# Testing

## How to run
```bash
npm test                              # existing suite + machine quick tier (ci/verify.mjs), ~13 s
npm run test:machine:quick            # machine quick tier alone, 159 tests, ~12 s
npm run test:machine                  # machine full tier, 232 tests (103 harness + 129 chip-model), ~90 s, ~240 s with the chip engine (not run by npm test or CI)
node ci/machine/selftest.mjs --filter "chip live"   # only the 51 live chip conformance tests (needs the chip engine), ~9 s
node ci/engine/build.mjs --upstream <clone of fm1-emu> --test   # build the chip-profile test engine and run its Rust tests (see ci/engine/README.md)
node ci/machine/chiptests.mjs         # the 129 flash-chip reference-model tests alone, ~0.3 s
node ci/machine/cli.mjs --fw felucca --corrupt erase:0x20000 --expect crashed
```
**Tiers (Component 3).** A machine test is quick if declared `test.quick(...)` in `ci/machine/selftest.mjs`; the full tier runs every test, so quick is a subset by construction. Quick tests run no firmware longer than the Felucca boot smoke test. `npm test` runs the quick tier through `ci/verify.mjs` with a **20 s hard timeout**; a failing quick test, a timeout, or an empty selection fails `npm test`. Output ends with `PASS: N machine tests (quick|full)`.
`cli.mjs` exit codes: 0 verdict matched `--expect`, 1 mismatch, 2 usage error or package would not boot.

## Results on record (2026-11-13, Windows 11, Node 24.19.0)
- `npm test`: PASS, 277 firmware packages (hashes, identities, order, source manifest, resource loader).
- Harness self-test: **105/105 pass** (30 harness tests: 16 Component 1 + 14 flash-ID, unchanged; plus 75 chip-model tests from Component 4 Stage A). Felucca 1.8.2-beta, AURORA 0.9.1, Melodee 1.6.1 boot headless (3 s) and show a screen.
- Repeatability: two boots of Felucca give identical LCD hash, flash hash and engine clock (interpreter, no input).
- Corruption on Felucca: zero `0x4000` -> `blank`; erase `0x20000` -> `crashed` (CPU halt). Fixture-specific; other firmware may differ.
- Speed: about 1x real time at 100 MHz interpreter (3 s emulated ~ 3 s wall); stuck-loop runs can cost far more (one case ~14 s for 2 s of audio).

## Known limitations (tests named `KNOWN LIMITATION` in selftest.mjs)
- Boot-area sector `0x0`: corrupting it has no effect (boot ROM/loader not run).
- Chip-key sector `0xFF000`: blank in the emulator and unused; corrupting it has no effect.
- Flash ID: selectable only as ID bytes on the shipped engine (Component 2). The chips' other behaviour is specified by the reference model (Component 4 Stage A) and emulated only by the separately built chip-profile engine (`flashChip`, Stage C); the **shipped** engine still has instant program/erase, no WIP, no write-enable check on program, no page wrap, no protection.
- Not available in the shipped engine: native ID export, flash fault injection, reset counter, flash timing, chip profiles, real update loader/USB OTA.
- **Chip-profile engine limitations:** array changes at accept, not at the end of a cycle (D33); (non-volatile status bits are now carried across `powerCycle()`, D40); no USB host; no JIT comparison; `FM1_FLASH_CUT` not honoured; behaviour the datasheets leave open is ignored and counted, not emulated; no firmware-behaviour tests under a profile yet beyond the two live smoke checks (Stage C4).
- **Known XIP-tail difference (documented, not investigated):** the shipped engine and upstream v0.3.0 differ in 3,488 of the 585,728 bytes of the decoded XIP window (flash offsets `0x9225B-0x93000`, the end of the window): the shipped engine shows erased bytes there as `0xFF`, v0.3.0 shows scrambled-looking values. Present at boot for every firmware, reproducible, no behavioural difference seen in any compared run. It applies to the chip-profile engine too, since that is v0.3.0-based.

## Not tested
JIT mode, the chip-profile engine under the JIT, input injection (key/encoder/MIDI paths are written but untested), `--flash`/`--save-flash` file round trip through the CLI, firmware other than the three above, other OSes.
